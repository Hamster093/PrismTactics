# PrismTactics 性能报告 v1.2

> 状态：**已整理**。1.1 的 HUD/对象池数据来自 `Docs/PerfData` 的原始采样；1.2 的 UI 图集部分为同会话 A/B 复测。文中标“未测”的项不要当结论。
> 对照基线：`Docs/Performance_v1.1.md` + `Docs/PerfData/perf_player_final.*`。
> 本轮改动：战斗道具（急救包）、范围/高亮格子池化、UI 图标 SpriteAtlas。

---

## 0. 一句话结论

- **HUD 事件化 + 对象池预热是最大单点收益（1.1 阶段）**：同一 60 敌峰值窗口，GC 748.9 → 218.2 B/帧（−71%，P95 1000 → 300），主线程 0.500 → 0.289 ms（−42%）。HUD 事件化完成时的中间值是 244 B/帧。
- **对象池削的是尖峰**：血条/弹道/飘字预热后，`Instantiate` 从单帧 6 次 49 KB 降到 0；对平均帧影响有限。
- **UI 图集对整帧 Draw Calls 无可见影响**（169 → 169），UI 批次 12 → 10；169 里 120+ 来自 60 个 Spine 单位，UI 只占约 6%。
- **1.2 编辑器复测的 GC 偏高（~775 B/帧）不是游戏逻辑**：Profiler 显示其中约 1.4 KB/帧来自基准浮层的 `GUI.Repaint`（IMGUI），已在采样期间关闭浮层。

## 2. 测试设置

| 项 | 值 |
|---|---|
| 场景 | `M1_Perf60`（60 敌人，固定地图/相机/波次/部署） |

| 热更 | **不加载**（压测只跑 AOT 内容，保证跨版本可比） |
| 采样窗口 | 同屏 ≥ 峰值 80% 的帧（与 1.1 同一规则） |

| 重复次数 | 每个配置 2 次，取趋势一致的一组；差异大时补第三次 |

### 2.1 图集前后怎么切
```text
A. 图集前：菜单 `Tools → PrismTactics → 诊断 → 禁用 UI 图集（编辑器内）` → 重新进 Play
B. 图集后：再点一次恢复 → 重新进 Play
```

两次都不重新出包，只切编辑器内资源，保证除图集外条件一致。

### 2.2 哪些对比是有效的

| 对比 | 有效？ | 原因 |
|---|---|---|
| 1.1 基线 vs 1.1 优化后 | ✅ | 同一次编辑器会话、同场景、同浮层状态（`Logs/Perf` 10/31 同一小时） |
| 1.2 图集开 vs 关 | ✅ | 同会话、同场景，只切图集 |
| 1.2 浮层开 vs 关 | ✅ | 同上，用来定位 IMGUI 干扰 |
| 1.1 编辑器 vs 1.2 编辑器 | ❌ | 会话不同（面板、Stats、Profiler 状态都不一样） |
| 1.1 编辑器 vs 1.2 Player | ❌ | 编辑器 vs 发布包，口径不同 |
| 1.2 Player vs 1.2 Player | ✅ | 同包、同机、同场景 |

> 结论：**跨版本不比绝对值，只比"同一次会话内的前后"**。
> 1.1 阶段可核验的是 748.9 → 218.2 B/帧（−71%），原始数据在 `Docs/PerfData/perf_baseline.md` 与 `perf_after_pool_warm.md`；
> `2756 → 244（−91%）` 没有原始采样文件，不作为结论。
> 1.2 不需要和 1.1 横比，只需要证明"在同一会话里，图集/池化没有让指标变差"。

> 如果确实要 1.1 ↔ 1.2 的 Player 对比，可以用 `git worktree` 检出 1.1 提交（`13f041c`）单独构建一版 Player，
> 成本约一轮构建 + 两次压测，属于可选项，不是必须。

> 口径说明：1.1 基线部署了 5 个干员且未加载热更（黑骑士技能空放）；
> 1.2 复测固定 4 个 AOT 干员，进一步减少变量。

## 3. 结果

### 3.1 图集前后（同一场景、同一帧窗口）

| 指标 | 图集前 | 图集后 | 变化 |
|---|---:|---:|---:|
| Canvas 批次（UI） | 12 | 10 | −2 |
| Draw Calls（整帧） | 169 | 169 | 噪声内 |
| SetPass Calls | 43 | 44 | 噪声内 |
| Used Textures | 19 | 19 | — |
| 主线程 平均（ms） | 0.422 | 0.447 | +0.025 |
| 主线程 P95（ms） | 0.673 | 0.643 | −0.030 |
| GC 平均（B/帧） | 779 | 775 | −4 |
| GC P95（B/帧） | 800 | 800 | 0 |

运行时证据（Console）：

```text
[UIAtlas] 图集已加载，spriteCount=40
[UIAtlas] ui_pause → texture=sactx-0-2048x2048-BC7-UIHandDrawnAtlas
```

### 3.1.1 截图口径

`before_gc.png` / `after_gc_steady.png` 是 **HUD 事件化 + 缓存** 的稳态帧 A/B：

- 优化前：`PlayerLoop GC 2.0 KB`，其中 `BattleHudBinder.Update` 0.7 KB / 23 次 `GC.Alloc`；
- 优化后：`PlayerLoop GC 1.0 KB`，HUD 分配消失，剩余主要是基准浮层的 `GUI.Repaint`。

这两张图不能证明 `2756 → 244`。`2756` 没有保留原始采样文件，已从结论中移除；引用截图时只能说“HUD 每帧 0.7 KB 分配消失”。

结论：

- 图集**确实生效**（Sprint 打包成功，取到的是 2048 BC7 图集页），UI 批次 12 → 10；
- 但**整帧 Draw Calls 没有可见变化**（169 附近，差异在噪声内），因为 169 里 120+ 来自 60 个 Spine 单位，UI 只占约 6%；
- 图集对 CPU 侧（主线程、GC）没有可测影响，符合预期——它优化的是渲染提交次数，不是 CPU。

> 编辑器 Profiler 数字含编辑器自身 UI，看前后相对变化，不看绝对值。

### 3.2 与 1.1 基线对比（峰值窗口）

| 指标 | 1.1 | 1.2 | 变化 |
|---|---:|---:|---:|
| 主线程 ms（均值 / P95） | 0.343 / 0.536 | 0.447 / 0.643 | 口径不同，见下 |
| GC B/帧（均值 / P95） | 244 / 300 | 775 / 800 | 主要来自测量浮层 |
| Draw Calls | 131 | 169（帧状态不同） | 不可直接比 |
| SetPass Calls | 33 | 43~44 | 不可直接比 |
| 同屏敌人 | 60 | 60 | — |

> **1.2 的 775 B/帧已定位到测量工具**：Profiler 的 CPU Usage 里，
> `GUI.Repaint` 单帧分配 **1.4 KB**（`GUILayout.BeginGUI` / `PerformanceBenchmarkRunner.OnGUI`），
> 属于基准浮层的 IMGUI 开销，不是游戏逻辑。现在采样期间会自动关闭浮层。
>
> 1.1 的 244 B 是当时浮层关闭/未绘制时的数字，因此两次不可直接横比。
> 跨版本比较只认同机同会话、同浮层状态下的 A/B；绝对值以 Player 包为准。

## 4. 解读

- **图集生效了**：运行时日志里贴图名是 `sactx-0-2048x2048-BC7-UIHandDrawnAtlas`，UI 批次 12 → 10。
- **整帧 Draw Calls 没降**：169 里 120+ 来自 60 个 Spine 单位（每个单位多个材质/网格），UI 只占约 6%，所以 UI 图集的天花板就是 10 个左右的批次。
- **剩下的 UI 批次不是图标**：文字（字体图集）、Mask/RectMask 强制的断批、尺寸超 600 没进图集的背景大图。
- **为什么帧率不变**：16.67 ms 预算下 CPU 不是瓶颈；本轮优化的是提交次数和一次性开销，不是把 60 帧变 120 帧。
- **为什么停止继续抠 UI**：按测量结果，继续投入 UI 最多再省 3~5 个批次；同样的预算投到 Spine 合批/实例池收益高一个量级。这是"先测量再决定投入"的取舍，不是做不动。

---

## 5. 局限

- 单场景、单机（Windows 编辑器 + Development Build），没有低端机、没有长时间挂机；
- 完整立绘（非裁切版）仍在图集外，详情面板单张加载；
- 图集 2048 会拆 2 页，页与页之间不合并；
- 编辑器 Profiler 含编辑器自身 UI，绝对值与真机不同，只比前后趋势；
- Spine 单位是当前 Draw Calls 的主要来源，本轮未处理。

## 6. 面试口径

### 6.1 30 秒版

> 1.1 我把 HUD 每帧刷新的事件化和缓存做完，GC 从 749 降到 244 B/帧，主线程 0.50 → 0.34 ms；随后对象池预热把峰值窗口做到 218 B/帧、0.289 ms。
>
> 1.2 我继续做渲染侧：把 HUD、技能、藏品的 35 张小图加 5 张裁切立绘收进一张 2048 的 BC7 SpriteAtlas，运行时统一走图集取名，并验证贴图确实来自图集页。UI 的 Canvas 批次从 12 降到 10。
>
> 但整帧 Draw Calls 还是 169 左右，因为 120+ 来自 60 个 Spine 单位，UI 只占 6%。所以我按测量结果停在这里，没有继续在 UI 上投入——下一个量级的收益在 Spine 合批和实例池。

### 6.2 追问准备

- **为什么 UI 批次只降了 2？** 因为图标本来就只占少数批次；剩下的是文字、Mask 断批和未进图集的背景大图。图标本身已经合并成 1 批。
- **怎么证明图集真的生效？** 运行时打印 `texture=sactx-0-2048x2048-BC7-UIHandDrawnAtlas`，不是原来的单图名；同时 `spriteCount=40`。
- **为什么是 2048 而不是 4096？** 显存减半（2048 BC7 约 4 MB/页，两页共 ~8 MB；4096 单页约 16 MB），代价是多一次批次。
- **为什么不让所有图都进图集？** 背景板单张就 1136×320 甚至 5333×3000，进图集会挤爆页并拉高显存；它们各自只出现一次，不需要合批。
- **为什么没继续降 Draw Calls？** 因为瓶颈是 Spine 而不是 UI；要降就得改 Spine 的材质/图集合并，属于另一轮工作量，先记录在案。
- **编辑器数字可信吗？** 绝对值不可信（含编辑器 UI），但同会话 A/B 的相对变化可用；正式数字以 Player 包为准。
